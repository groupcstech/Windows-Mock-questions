**Window Programming: Pre-Mid Mockup Answers**
Brief answers to Questions 1–9, each following its stated Discussion Focus.
**Part 1: Software Development, Methodologies & Principles**
**1. Choosing the Right SDLC Model**
Software engineering is layered: tools, methods, process, and quality focus as the base. The model you pick is the "process" layer, and it must match the project's size, risk, and requirements stability.
(A) Flight-control software calls for Waterfall or Spiral. Its requirements are fixed and safety-critical, and failure is unacceptable, so it needs heavy documentation, formal verification, and certification. Spiral adds repeated risk analysis at each loop.
(B) The food-delivery startup app calls for Agile/Scrum or RAD. The market changes quickly, so requirements will change, and short sprints and prototypes give fast releases and customer feedback.
Three factors drive the choice. Requirements stability: stable requirements favor Waterfall, while changing requirements favor Agile/RAD. Risk tolerance: low tolerance favors Spiral or Waterfall, while high tolerance allows Agile/RAD. Timing of testing: late testing is acceptable only when requirements are stable and failures are cheap. Safety-critical work needs rigorous, planned testing, whereas Agile tests continuously in every sprint.
**2. The Hidden Trade-offs of RAD**
RAD gives time-boxed delivery and prototyping over heavy planning, which means faster time-to-market and happier customers. The trade-off is that little upfront design is done. Prototypes often become the final product, which creates architectural debt (tight coupling, quick fixes, poor structure), so adding users and features later gets harder and costlier and scalability is reduced.
Without designing for load, failover, and fault handling, the system is also unreliable when users demand high availability. The lack of deep risk analysis means technical and security risks are found late, when they are expensive to fix. Therefore RAD is not suitable for large-scale or mission-critical systems.
**3. Balancing Software Development Principles**
DRY means don't repeat code, KISS means keep the design simple, YAGNI means don't build what isn't needed yet, and Separation of Concerns means splitting the program into parts with distinct responsibilities. Yes, they can conflict: pushing DRY or Separation of Concerns too hard adds abstractions and layers, which violates KISS and YAGNI.
For example, take a program that prints "Hello". An over-engineering developer creates IMessageProvider, MessageFactory, MessageService, MessageRepository, and a DI container. One method would do, so this is many classes for a feature that may never change. The lesson is that these are engineering trade-offs, not acronyms to memorize, so abstract only when real duplication or complexity appears.
**4. The Economics of Testing and Code Quality**
The cost of an error is lowest early because fixing it in requirements or design means editing a document. Later, the defect is built into code, tests, and other modules, so rework spreads. After deployment, user impact, emergency patches, downtime, and reputation loss add to the cost. Early defects compound into design and code flaws if they are not caught until late testing. Waterfall tests late, so defects are found when they are most expensive, whereas modern practices test early.
TDD (the testing principle) writes tests first, so defects are caught as code is written, and the tests act as a safety net for later changes. Continuous Integration merges and tests code automatically and often, so integration errors show up immediately. Peer code review (the code review principle) has a second person find logic, design, and standards flaws before they spread. Together they find defects early and keep the cost of correction low.
**Part 2: .NET Architecture, C#, and Window Programming**
**5. MSIL, JIT, and the Platform Independence Paradox**
C# source compiles to MSIL, a CPU-independent intermediate code, and the JIT compiler converts it to native machine code for the actual processor at run time.
.NET Framework apps were still platform-dependent because only the code is CPU-independent. The CLR and class libraries (Windows Forms, registry, Win32 APIs) are OS-dependent and exist only on Windows. Mono changed that: it is a third-party, cross-platform runtime and library implementation for Linux, macOS, and others, and it runs the same MSIL without Windows.
**6. Managed vs. Unmanaged Code and Language Interoperability**
Managed code is protected by CLR services. Garbage collection prevents memory leaks and dangling pointers, type safety blocks invalid casts and type misuse, metadata lets the CLR verify types and code, and array bounds checking prevents buffer overruns. Unmanaged (Win32) code has none of these safeguards, so it is prone to leaks, crashes, and security holes.
For interoperability, all .NET languages compile to MSIL and share the CTS. C# string and VB.NET String both map to System.String, which derives from System.Object. Both parts therefore agree on types, and one team can use C# and VB.NET in one application without data conflicts.
**7. Solving "DLL Hell"**
The problem was that installing one app overwrote a shared DLL and broke other apps. .NET solves it with assemblies, self-contained deployment units (.exe/.dll). Private assemblies sit in the app's own folder, so other apps can't overwrite them. The manifest/metadata records the assembly's identity, version, and dependencies, so each app knows exactly what it needs. Strong names (name + version + culture + public key) make assemblies unique and tamper-proof.
The GAC holds shared assemblies and allows multiple versions side by side, so each app runs against the version it was built with.
A namespace is a logical grouping of classes (naming and organization), while an assembly is a physical grouping (the .exe/.dll deployment unit). One assembly can hold many namespaces, and one namespace can span many assemblies, so the terms are not interchangeable.
**8. Abstraction in Data Access: ADO.NET vs. Entity Framework & LINQ**
Raw ADO.NET is error-prone because developers manually open and close connections, write SQL strings (typos show up only at runtime), manage transactions, and convert DataSet rows and columns to objects and back.
Entity Framework (ORM) automatically translates relational tables into .NET objects, so you work with classes and properties instead of SQL and connections. LINQ adds one standard, compile-time-checked query syntax across SQL, XML, and in-memory collections. The gains are less boilerplate, fewer errors, faster development, and cleaner code. The trade-offs are less control over the generated SQL, possible performance overhead, and a learning curve.
**9. Under the Hood of Event-Driven Programming**
A console app runs sequentially from Main() and exits at the end. A Windows Forms app waits for the user, so the user drives the flow (the event-driven paradigm). Application.Run(new Form1()) in Main() starts the main loop (message loop), which waits for messages from the OS and dispatches them until the form closes.
When the user clicks a Button, the OS detects the click and puts a message in the app's message queue. The main loop takes the message and dispatches it to the Button control, which raises its Click event, a notification that something happened. The event listener (subscriber) is the code registered to that event. Registration uses a delegate, a type-safe method pointer: button1.Click += new EventHandler(button1_Click);. A lambda expression can replace it: button1.Click += (s, e) => MessageBox.Show("Hi");. Finally, the event handler method (button1_Click(object sender, EventArgs e)) runs your code, and control returns to the main loop to wait for the next event.
This connects the theory (slides 94–97) to WinForms controls, properties, and events (slides 105–106). A control such as the Button has properties (Text, Enabled) and events (Click, MouseEnter), and the event, delegate, and handler mechanism is how those control events are wired to your code.
